# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A remote **MCP server** ("Senegal Maths — TLM") that helps experts author teaching materials (pupil manuals + lesson sheets) from a curriculum knowledge graph. It exposes MCP tools, not a UI. The graph lives in Firestore as the raw *Learning Commons* (LC) ontology; generated `.docx` files + their history live in Firebase Storage; auth is Supabase JWT. Work is always scoped to an active `(workspace, grade, subject)` via `set_context` — the **workspace** is the tenant that owns a set of graphs (the two current graphs are the `senegal` workspace) and is the first segment of every namespace/storage key; roles are **per workspace** (see `docs/design-notes/workspaces.md`). Document generation is LLM-driven — the server provides curriculum context, prompts, signed upload URLs, and history; it never renders a `.docx` itself.

## Communicating with the user

Explain in **plain language** — avoid jargon, and define any technical term you must use. When explaining a concept or weighing a tradeoff, ground it in a **concrete example**: a small worked case, real numbers, or an analogy. Abstract prose on its own is hard to follow. Lead with the plain answer, then show it. This applies to every explanation, not only when asked.

## Repo layout

The server is a self-contained package under **`backend/`** (`backend/src`, `backend/scripts`, `backend/test`, `backend/assets`, its own `package.json`/`tsconfig.json`/`Dockerfile`); the KG explorer UI is its own package under `frontend/`. **Run every command below from `backend/`** (`cd backend` first), and read every `src/…`, `scripts/…`, `test/…`, `assets/…` path in this file as relative to `backend/`.

## Commands

```bash
npm run build          # check-cycles + tsc → dist/  (Docker build runs this)
npm test               # vitest run (all suites)
npx vitest run src/server/__tests__/preview.test.ts        # a single test file
npx vitest run -t "reflects a staged edit"       # tests matching a name
npm run typecheck      # tsc --noEmit
npm run check:cycles   # layering + import-cycle check (also part of build)
npm run start          # stdio MCP server (dist/index.js)
npm run start:http     # HTTP MCP server (dist/http.js) — remote/Cloud Run mode
npm run import:kg-store -- <workspace> <grade> <subject> <graph.json>  # import a new KG into Firestore (needs creds)
npm run export:kg-store -- <workspace> <grade> <subject> [out.json]    # export a namespace's published graph (backup / interchange)
```

Tests use `vitest` and never touch real Firebase/Firestore: a **memory KG store** (`createMemoryKgStore` + `__setKgStoreForTest`) and a **fake StorageAdapter** (`__setStorageForTest`) are injected, seeded from the committed graphs under `test/fixtures/` (via the `src/__tests__/index.ts` helper — importing it also registers the fixture contexts). Follow `src/kg-store/__tests__/lifecycle.test.ts` / `src/server/__tests__/preview.test.ts` for new suites.

## Module layering (enforced)

`npm run check:cycles` (run automatically by `build`) fails on any import cycle **and** on any import that points "up" a layer. Imports only ever point **down**:

```
app       server/* · index.ts · http.ts · activate.ts
adapters  adapters/*                          — one behavior module per subject
services  storage/* · curriculum/* · generation/* · kg-store/* · kg-recipes/*   — never import adapters
core      config.ts · types.ts · context/{state,shared} · utils/*   — leaves
```

Consequences: `kg-store/` is **subject-agnostic** (it knows nodes/edges, never "chapter"/"bilan"); `kg-recipes/` (the generic curriculum verbs) composes `kg-store`'s primitives, importing it one-way through its barrel (kg-store never imports back). Anything subject-specific is injected from the app layer (e.g. the preloaded `CurriculumModel`). `curriculum/store-bridge.ts` owns the `CurriculumModel ⇄ nodes/edges` round-trip so `kg-store` and `adapters` never depend on each other. `context/state.ts` is a dependency-light leaf; the adapter resolution + schema guard that need `storage`/`adapters` live in root `activate.ts` to avoid a cycle. A new top-level module must be added to the `LAYERS` map in `check-cycles.mjs`.

## Subject-adapter architecture

Both subjects share the converged `{ nodes, relationships }` envelope in **canonical Learning Commons** (see `docs/design-notes/canonical-lc-migration.md`): real LC labels (`Lesson`/`LessonGrouping`/`Activity`/`Course`/`Material`/`StandardsFrameworkItem`/`LearningComponent`), **camelCase** props (`normalizedStatementType` = container vs leaf; `statementType` = category on leaves; `description` = text/title; ordinal in `position`), containment split across `hasPart` (content) + `hasChild` (standards hierarchy), and alignment across `hasEducationalAlignment` (content→SFI) + `supports` (component→SFI). Our non-canonical extras (extraction provenance, reading's palier/genre, `metadata.role`) live verbatim in a `metadata` **extension sidecar**. The shared *parse* is one generic traversal (`curriculum/parse-graph.ts::parseGraph`): a node's **kind is its own canonical value** — a `LessonGrouping` by `groupName` (`Chapitre`/`Semaine`/`Jour`), a `StandardsFrameworkItem` by `statementType` (`Objectif spécifique`, `Grade`, `Theme`, … — falling back to `normalizedStatementType` when empty), and every content leaf by its LC `label` (`Lesson`/`LearningComponent`/`Activity`/`Material`). No `metadata.role`. A unit's ordinal comes from `numberFrom` (maths reads `metadata.order`; reading reads `position`), **except standards** (`StandardsFrameworkItem`), which carry **no ordinal** — they sequence by graph traversal (any source ordinal on a standard, e.g. the maths spine's `metadata.order`, is deliberately ignored). Each subject is a **declarative `SubjectProfile`** (`src/adapters/profiles/*.ts`, Zod-validated) built into a `SubjectAdapter` by one generic factory (`src/adapters/build.ts`), keyed by `(grade, subject)` in `src/adapters/index.ts` — no per-subject behavior module. See `docs/design-notes/authorable-catalog.md`.

**CI maths is graph-native** — authored teaching content lives in the LC **content layer**, distinct from the standards **spine** (see `docs/design-notes/graph-native-authoring.md`, live). A *chapter* is a content `LessonGrouping` (label-keyed; its type is `groupName` — Chapitre/Unité/Module); a *lesson* is a content `Lesson` node that `hasEducationalAlignment` to its spine `expectation` (the objectif spécifique — an own kind that keeps the OS text + components/tasks). A lesson has two containment parents: its grouping via `hasPart` (content axis) and its week via `hasChild` (schedule axis). The **bilan** is explicit data (`educationalUse: "Assessment"` on the Lesson), not a parse-time heuristic. **CE1 reading has the same content layer**: each week is a `LessonGrouping` (kind `week`) holding **`Jour 1–5` day `LessonGrouping`s** (kind `day`, `groupName "Jour"`), each holding that day's session `Lesson`s (Scope B: 22 sessions/week across the 5 days), which `hasEducationalAlignment` the spine standard they teach. So both subjects share the LC content-layer labels + alignment structure — the grouping's read-*kind* (chapter vs week) is the remaining subject-specific projection. (Maths also carries **RECE + six other "Composants dérivés" frames**: each is a `StandardsFrameworkItem` holding derived `LearningComponent`s and illustrative `Activity`s directly via `hasChild`. Each illustrative Activity `hasEducationalAlignment`s a **standard** (its component's parent SFI) and carries the specific component it exemplifies in `metadata.illustratesComponent = {id, name, order}` — canonical LC has no Activity↔LearningComponent edge. `buildSlice` surfaces these as a lesson's per-component illustrative tasks.)

- Adapters are **behavior only**: `detect`/`parse`, plus `capabilities`. No schema/integrity lives on the adapter — write-safety is in the write tools; subject coverage is no longer a coded adapter hook (it's authored prose in the guide, checked by `review_draft`). A document's identity is the **graph node it covers** (its scope node), so the profile no longer carries a `deliverables` enum (see `docs/design-notes/graph-linked-documents.md`). The curriculum recipes are **generic** now (`kg-recipes`), so an adapter no longer declares a `recipeProfile`/`structuralAliases`/`lcNodeTemplate`, and there is no wording-edit surface. Subject-agnostic adapter behavior — the model loader (`makeEnsure`) and the generic `detect` (`detectEnvelope`) — lives in `src/adapters/engine.ts`; each subject is a declarative `SubjectProfile` supplying only what genuinely differs (its parse descriptor + capabilities), assembled by `src/adapters/build.ts`. The bilan flag is canonical (`educationalUse: "Assessment"` → `isAssessment`, set in `parseGraph`), not a per-subject hook.
- Each stored node keeps its raw LC fields under `properties.raw`, its top-level LC `labels`, and (spine nodes) normalized fields (`title`/`text`/`order`/`isAssessment`) alongside. `id` is the LC UUID verbatim. A node's content, ordinal, and title are edited in place through the generic verb `edit_node`, not a wording tool. `add_node`-created nodes derive their LC identity (`labels`/`normalizedType`/`normalizedStatementType`/`metadata.role`, and the raw ordinal path(s)) by **copying an existing node of the same label from the graph** (canonical LC defaults when none exists yet), so they round-trip through the parser.
- **Firestore is the only KG store** (there is no bundle/`KG_SOURCE` mode — see `docs/design-notes/firestore-only-store.md`). `activateContext` hydrates the `CurriculumModel` once from the namespace's **published slot** and pins it in the session bag under `PRELOADED_MODEL_KEY`; adapter sync reads (`ensure()`) read from there. It **also** reads the published **profile config cell** and builds the adapter from that stored `SubjectProfile` (the store is the live source of truth for a subject's config; an invalid stored profile is refused, and a namespace with no cell falls back to the in-repo literal). **Context discovery** comes from the store too: `activate.ts::refreshAvailableContexts` lists the store's namespaces (`listNamespaces` → `parseNamespace`) at startup and installs them via `context/state.ts::setAvailableContexts`, so `listAvailableContexts` reports what the store holds — no on-disk `sources/` scan. A new graph is added with `import-kg` and backed up with `export-kg`; `terminology.json` (the FR/Wolof glossary fallback) is the one on-disk per-subject asset, under `assets/<ws>/<grade>/<subject>/`.

## Full-graph store + faithful re-export

The Firestore store holds the **complete raw LC graph**, not just the curriculum spine: every raw node (spine nodes tagged `spine:true` + normalized fields; framework/derived nodes `spine:false` + `raw` only) and every raw edge with its real type — `hasChild`/`hasPart`/`supports`/`hasEducationalAlignment`/`relatesTo`/`buildsTowards`. Hydration rebuilds the raw envelope (`store-bridge.ts::toRawEnvelope`) and re-runs `adapter.parse` to derive the spine model. Because the store *is* the raw graph, `toRawEnvelope` also reproduces the source JSON — that is what `export-kg` writes (and `import-kg` reads back). The KG explorer (`src/kg-export.ts`) follows the **LC ontology only**: every node is categorized/coloured by its LC **label** (`StandardsFramework`/`StandardsFrameworkItem`/`Course`/`LessonGrouping`/`Lesson`/`Activity`/`Material`/`LearningComponent`), and it offers two generic views — a **containment hierarchy** (walk `hasChild`+`hasPart` from the framework root) and **by-label** — with no subject vocabulary (no domaine/chapitre/semaine/strand/palier). The detail panel renders the node's raw LC properties generically. `supports` and `hasEducationalAlignment` fold (reversed) into the display containment tree so components/lessons stay reachable (display-only; the store keeps the real edges).

## Draft/published + the curator loop

The KG store is **double-buffered**: two slots (`a`/`b`) behind a pointer `{ publishedSlot, draftSlot }`. Reads and generation resolve to **published**; edits stage onto the **draft**; `publish_draft` is an **atomic pointer flip**. `createDraft` snapshots published byte-for-byte (ids preserved). The **subject profile** rides this same pointer as a per-slot **config cell** (like the `meta` stamp) and is a **`{ core, guide }` record** (phase 2c): `core` is the machine `SubjectProfile` the parser/classifier consume; `guide` is authored markdown the authoring/generating LLM reads (via `get_graph_guide`) — reads consume only `core`, the guide never sits on the read hot path. `get_profile` reads the record, `edit_profile` stages a full-replace onto the draft (two-phase, curator-gated; `core` Zod-validated + `guide` length-checked at authoring time), and it publishes/discards with the graph — so `diff_draft`/`publish_draft` surface a staged profile change as `profileDiff` and the publish token folds in the profile hash. A legacy flat `SubjectProfile` cell (pre-2c seed) still resolves (`{ core: raw }`). The guide carries the subject's **coverage expectations in prose** (the coded coverage rules were retired — no more automatic coverage warnings on edits / `diff_draft` / publish); **`review_draft`** (read-only) bundles those expectations with a subject-agnostic structural snapshot for the calling model to reason over — the server never runs the review itself. See `docs/design-notes/authorable-catalog.md` (phase 2b/2c).

Every graph mutation is **two-phase** (`kg-store/mutations.ts::runGraphMutation`): a dry-run returns a diff + warnings + an opaque `confirmationToken` (no state change); the confirm re-checks the token (base version current, nonce unused, mutation+args match) then applies to the draft only. Roles (`authz.ts`) are **per workspace** (derived from the namespace's first segment): `curator` may apply/discard, `approver` also publishes, `admin` also manages the workspace's members, and an env-rooted `super_admin` spans every workspace; unknown/no-membership actors can still read+generate but can only *enter* (`set_context`) a workspace they hold a role in. Memberships live in a Firestore registry (`src/workspaces/`), read once per request into `Actor.memberships`; a legacy Supabase `app_role` still bridges to the `senegal` workspace during migration. Tenant admin tools: `list_workspaces`, `create_workspace`, `add_member`/`remove_member`/`list_members`. See `docs/design-notes/workspaces.md`. Every mutation and denial is recorded in an **append-only audit** (`AuditRecord`), committed in the same transaction as the state write. `get_capabilities` is a read-only *mirror* — every field is sourced from the module that enforces it (never a copy), asserted by `capabilities.test.ts`.

Curriculum edits are exposed as **three generic, subject-agnostic verbs** (`kg-recipes/`, mirrored by `get_capabilities`): **`add_node`**, **`move_node`**, **`edit_node`**. They speak **pure canonical LC** — no chapter/domaine/week vocabulary, no per-subject `RecipeProfile` — and are available on **every** subject (validity is structural, not a per-subject allowlist). `add_node(parentId, label, …)` creates one node with an LC `label`, attaches it under the parent via the canonical containment edge (`hasPart` for content, `hasChild` for standards), at a `position`, optionally `alignTo` a `StandardsFrameworkItem` (`hasEducationalAlignment`); a free `properties` bag carries extra canonical LC props (content, materialType, studentGroupingType, educationalUse, groupName…) written under `raw.*`. The **skeleton comes from the graph**: the new node's identity (labels, `normalizedType`, role, raw ordinal path(s)) is copied from an existing node of the same label (canonical defaults for the first of its kind — e.g. reading's first Activity). `move_node` re-parents along one containment axis (a node's second axis — e.g. a maths lesson also scheduled under a week via `hasChild` — is left intact); `edit_node` edits a node's `content` (`MATERIAL_CONTENT_PATH`), `position` (ordinal — membership is the edge, so it never cascades), and/or display `title` in place (it consolidated `reposition` + `set_content` and added title editing) — the only field-edit path (there is no separate wording tool). A content `Lesson`/`Activity`/`Material` reads back via `buildSlice`; CI maths lessons still legitimately carry **two parents** (grouping via `hasPart` + week via `hasChild`). For authoring, **`add_nodes`** is the single node-creation tool (one node or many; it **retired the per-label typed adds** — each `kind`'s LC props are catalogued in `get_capabilities` under `editable.batch.kindProperties`) and **`create_edges`** the batched edge form. Each batch is one atomic draft edit → one token, one audit record; the response is a compact `counts` **summary by default** (`returnMode:"full"` for the whole diff), and an optional `idempotencyKey` makes a retried confirm a safe replay (namespace-scoped, 24h). The generic graph **reads** are **`walk_graph`** (one directional, filtered, paginated BFS — the single traversal primitive, which **replaced `get_course`**; `slot:"draft"` walks the unpublished draft) and **`namespace_stats`** (an argument-free orientation snapshot). See `docs/design-notes/graph-native-authoring.md`.

## Preview generation (isolated from published)

`preview_generation(course)` closes the editing loop: `diff_draft` shows the graph **diff**; preview shows the resulting **material**. It resolves the curriculum from the **draft slot** and returns the Course's containment subtree (the same read the published path exposes), keeping the published path byte-identical. Isolation is the invariant: output goes through `create_preview_upload_url` to a **segregated `previews/` prefix** (invisible to `reconcile`/`list_documents`) with short-lived, labelled URLs — never the canonical bucket, `log_generation`, or history. Role-gated like `diff_draft` (curator+approver); audited as a distinct `preview` event. See `docs/design-notes/preview-generation-findings.md`.

## Conventions & gotchas

- **Session model**: per-session in HTTP mode, process-wide in stdio. Context-derived caches (active adapter, preloaded model, history cache) live in the session **bag** and are cleared wholesale on `set_context`. Don't hold subject state across a context switch.
- **Read state is threaded, not shared**: adapter projections take the `CurriculumModel` as an argument (`buildGenerationContext(…, model?)`) so a draft-resolved read can't collide with a concurrent published read. Don't reintroduce a mutable per-adapter "current model".
- **Confirmation gates differ by lifecycle**: document tools (`create_upload_url`, `log_generation`, `record_document_content`) write **live** ("no draft, no undo"); graph mutations **stage a draft** ("nothing reaches generation until you publish"). Same envelope, deliberately different stakes.
- **Docs**: [`docs/technical-reference/`](docs/technical-reference/) is the operational manual (store & curator loop, explorer, generation/storage, deployment, add-a-subject) — one file per topic behind a README index; `docs/design-notes/*` hold per-subsystem design rationale (architecture, [`kg-mutations/`](docs/design-notes/kg-mutations/) the two-phase mutation framework, explorer, preview, audit, **graph-native authoring**). Each design note carries a **Status** line — heed "Historical / superseded" ones. **[`docs/reference/learning-commons/`](docs/reference/learning-commons/)** is the canonical **LC ontology** reference (node data models, all relationship possibilities, enums) — check it before adding/retyping any node or edge to stay canonical; its README lists our known deviations (`buildsTowards` between chapters, the `metadata` sidecar).
- **Writing code**: always apply the `write-reviewable-code` and `comment-code` skills when writing or editing code in this repo — descriptive names, one idea per line, small readable functions, and concise human-first comments (the *why*, not a restatement of the code).
- **Writing docs**: **one concern per file** — split by topic, never by length (a coherent-but-long note is fine; a file that mixes subsystems should be split into a folder with a README index, e.g. `docs/technical-reference/`). And **keep this file (`CLAUDE.md`) lean** — it is loaded into every session, so it stays a map: put detail in the linked docs above and point to them, don't inline it here.
- **Git**: `main` is the default; land changes via a branch + PR. Commit only when asked.
